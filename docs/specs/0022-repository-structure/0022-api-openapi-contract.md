# 0022. API OpenAPI contract

**Date**: 2026-10-04
**Status**: In Progress

## Summary

The NestJS API needs a reliable, reviewable contract for its Letterly routes. Generate OpenAPI from the existing route and Zod contracts, keep the interactive docs outside production, and attach a generated JSON contract to CI runs.

## Context

The engineering blueprint requires Swagger or OpenAPI for the protected API contract, and spec 0004 says to add it after registering the shared error envelope. The API currently uses Zod 4.4.3 at request boundaries through a local `ZodValidationPipe`, but it has no Swagger dependency or generated OpenAPI contract. Better Auth owns `/api/auth/*` through its SDK and should remain a separate contract surface.

The official NestJS OpenAPI guide documents raw schema metadata and Standard Schema integration. The project already uses Zod 4.4.3, but the installed Nest `@nestjs/common` 11.1.28 route parameter decorators do not expose the newer `schema` option. Zod exposes stable `z.toJSONSchema()` conversion with an OpenAPI 3.0 target and separate input and output modes, while Nest Swagger accepts raw request and response schema objects. A small metadata helper can bridge those APIs without upgrading Nest or replacing the existing runtime validation pipe.

## Requirements

**User stories**:
- As an API and web developer, I want a generated contract for Letterly's HTTP routes so clients and reviewers can inspect the real request, response, error, and authentication boundaries.
- As a contributor, I want to inspect the contract outside production and download the exact contract generated by CI without maintaining a second hand-edited API description.

**Acceptance criteria**:
- **AC-1**: Generate an OpenAPI 3.0 document for Letterly-owned routes: `GET /`, `/health`, `/ready`, and all routes under `/api/v1`. Do not include Better Auth's `/api/auth/*` endpoints; Better Auth remains the SDK-managed contract.
- **AC-2**: Request schemas come from the Zod schemas already used by the boundary validation pipe. Response schemas come from the existing shared contracts or from Zod response contracts owned by their feature. Documentation must distinguish input and output schemas and must not weaken, replace, or bypass runtime validation.
- **AC-3**: Each documented operation identifies its tag, summary, path/query/body inputs, success response, applicable session or visitor security, and applicable stable API error responses using the shared `apiErrorEnvelopeSchema`. Protected routes describe the Better Auth session cookie; public routes do not require it. Examples and descriptions contain no real user, credential, session, or confession data.
- **AC-4**: The interactive UI is mounted at `/docs` and its JSON route at `/docs-json` only when `NODE_ENV` is not `production`. Neither route is registered in production.
- **AC-5**: A package-level `openapi:generate` task writes a deterministic `apps/api/openapi.json` from the same document factory used by the nonproduction route. The generated file is ignored by Git and uploaded as a CI artifact named `letterly-api-openapi` after the API checks pass.
- **AC-6**: Tests verify route coverage, Better Auth exclusion, input/output schema shape, applicable security/error metadata, nonproduction route registration, and production route absence. Existing API request behavior and response envelopes remain unchanged.

## Options considered

### Option 1: Native NestJS Swagger and a small Zod 4 schema helper

Use `@nestjs/swagger` to discover Nest routes and attach raw OpenAPI schemas generated from existing Zod 4 input and output contracts through small local method decorators.

**Pros**:
- Reuses the existing Zod schemas and the current local validation pipe.
- Uses Nest's route discovery and standard OpenAPI decorators for summaries, security, and responses.
- Uses Zod's native JSON Schema conversion and Nest Swagger's raw schema support without changing the current Nest minor version.
- Keeps validation and documentation paired with the same Zod schema while adding only metadata helpers.

**Cons**:
- Existing controllers need explicit OpenAPI metadata for routes, errors, and security.
- Zod constructs that cannot be represented in JSON Schema must be represented with a deliberate HTTP-compatible schema or an explicit OpenAPI override; silently documenting them as unconstrained values would be unsafe.

### Option 2: Adopt `nestjs-zod` DTOs and decorators

Convert boundary schemas to `nestjs-zod` DTOs and use its validation, response, and Swagger decorators.

**Pros**:
- Provides a single integration package for Zod-backed DTOs and OpenAPI metadata.
- Supports Zod 4 and can generate request and response schemas.

**Cons**:
- Introduces another request/response validation layer alongside the existing custom pipe and shared error contract.
- Broadens the change from documenting existing routes into migrating controller boundaries, with risk to error envelopes and response serialization.
- Requires library-specific OpenAPI post-processing and maintenance in addition to Nest's native Standard Schema support.

### Option 3: Maintain a hand-written OpenAPI file

Describe routes and schemas in a separate YAML or JSON contract.

**Pros**:
- Allows complete manual control of the published document.
- Does not require runtime Swagger setup.

**Cons**:
- Duplicates the route and Zod definitions and will drift as categories, templates, and API features grow.
- Makes route completeness difficult to verify against Nest's actual controllers.

## Decision

**Chosen option**: Option 1: Use NestJS Swagger with native Zod 4 JSON Schema conversion and small local request and response metadata helpers.

Add `@nestjs/swagger` and configure a single document factory with OpenAPI 3.0 metadata. Add local method decorators for body, query, path parameter, success response, and API error metadata; each converts an existing Zod contract with `z.toJSONSchema(schema, { target: 'openapi-3.0', io: 'input' | 'output' })` and attaches raw schema objects through Nest Swagger. Keep each existing `ZodValidationPipe` in place and use the same imported schema for both validation and documentation. Use the shared API error schema for relevant error status responses. Select only the root, health, catalog, pages, and administration route modules; exclude `AuthModule` so Better Auth remains SDK-managed. Mount the UI and JSON document only outside production. Generate the identical document in CI and upload it as a workflow artifact.

## Rationale

Zod's official conversion API supports OpenAPI 3.0 and separate input and output modes. Nest Swagger accepts raw schemas for request bodies and responses. The current installed `@nestjs/common` 11.1.28 declarations do not support the newer `schema` argument shown in the latest Nest controller guide, so adding that argument directly would not typecheck without a framework upgrade. A local metadata helper avoids that upgrade while retaining the exact schema objects used by the existing validation pipe.

This approach minimizes drift while preserving current runtime behavior. It also makes documentation failures visible in CI: an unrepresentable schema or an undocumented route must be corrected explicitly rather than becoming a permissive `{}` schema. `AuthModule` stays outside the selected Swagger module list so its SDK-defined protocol is not duplicated.

## Feature design

**Data model sketch**: None. The contract is generated from route and Zod metadata; no database state changes.

**Runtime design**:
- Add a document factory under `apps/api/src/infrastructure/openapi/` with stable title, version, server path, operation IDs, component schemas, cookie security schemes, and route-module inclusion. Use `deepScanRoutes: false` and explicitly include `AppModule`, `HealthModule`, `CatalogModule`, `PagesModule`, and `AdminModule`; do not include `AuthModule`.
- Keep request validation in `ZodValidationPipe`. Add local `ApiZodBody`, `ApiZodQuery`, `ApiZodParams`, `ApiZodResponse`, and `ApiZodErrorResponse` method decorators that convert the exact schemas passed to boundary pipes or returned by feature use cases. Request conversion uses input mode; response conversion uses output mode; both target OpenAPI 3.0. Fail generation for unrepresentable schemas unless the owning feature adds a correct HTTP representation or explicit schema override.
- Mark protected API operations with the Better Auth session-cookie requirement and document the environment's secure-cookie name. Document visitor or page-unlock cookies only on public routes that actually use them. Public catalog, public page, health, and landing health operations have no session security requirement.
- Mount Swagger UI at `/docs` and the JSON document at `/docs-json` only in nonproduction startup. Reuse the same document factory in a `tsx` generator invoked from an `apps/api` package script. Write the artifact to `apps/api/openapi.json`; do not commit generated output.
- Add CI generation and upload after lint, type checking, tests, Prisma validation, and build succeed. The artifact is for review and client generation; it is not deployed as a production route or uploaded to a public hosting location.

**API surface**:

| Surface | Inputs | Outputs | Access |
|---|---|---|---|
| `GET /docs` | None | Swagger UI backed by the generated OpenAPI document | Nonproduction only |
| `GET /docs-json` | None | OpenAPI 3.0 JSON for Letterly routes | Nonproduction only |
| CI `openapi:generate` | Validated CI configuration and Nest route metadata | Deterministic `apps/api/openapi.json` and uploaded artifact | CI job only |

**Value sourcing**:

| Action | Value produced / displayed | Source |
|---|---|---|
| Operation path and method | OpenAPI path item | Nest controller and method decorators in the included modules |
| Request parameters | OpenAPI input schema | Existing Zod schema passed to the request `ZodValidationPipe` and converted by the local Swagger metadata helper |
| Success response | OpenAPI output schema and status | Existing feature response contract or a new feature-owned Zod response schema, with `z.toJSONSchema` output conversion |
| Error responses | HTTP status and safe envelope | Controller behavior, global `ApiExceptionFilter`, and shared `apiErrorEnvelopeSchema` |
| Authentication | Cookie security requirement | `BetterAuthSessionGuard` on protected routes and Better Auth's configured session cookie |
| Nonproduction route availability | `NODE_ENV` check | Validated application configuration |
| CI artifact | Generated JSON content | The same OpenAPI document factory used by nonproduction Swagger routes |

**Key invariants**:
- OpenAPI metadata is descriptive only and does not replace runtime guards, Zod parsing, authorization, or safe response mapping.
- A request schema and its validator must refer to the same Zod schema object; route docs do not copy shapes into DTOs or handwritten OpenAPI definitions.
- The route decorators use the currently installed Nest Swagger raw schema support; implementation must not pass the unsupported `schema` option directly to Nest 11.1.28's `@Body`, `@Query`, or `@Param` decorators.
- Better Auth endpoints are excluded from the document; user account and session behavior remains defined by the Better Auth SDK.
- Public APIs never claim session authentication unless their controller actually enforces it. Protected endpoints document the cookie-based session, and public visitor cookies remain operation-specific.
- The shared `apiErrorEnvelopeSchema` is reused rather than restating a second error envelope. Route decorators list only applicable error statuses.
- Unrepresentable Zod types fail generation. No default `unrepresentable: 'any'` or hand-authored permissive fallback may hide missing API modeling.
- No secrets, session identifiers, private page content, real page slugs, or user-submitted content appear in examples or CI metadata.
- `/docs` and `/docs-json` are absent in production even though the CI artifact is available for review.
- The generator is an `apps/api` package task. CI invokes that task directly; no root script duplicates package task logic.

**Security model**: The CI artifact contains public route shapes and protected request/response schemas but no user records or secret values. The interactive document route is not exposed in production. Protected operations state that a Better Auth session cookie is required; the documentation does not weaken server authorization or CSRF checks. Better Auth account endpoints are not copied into this contract.

**Configuration required**: None. The server definition is relative to the API origin; route exposure uses validated `NODE_ENV`. Generation uses the same required CI environment values as API tests and does not connect to live services.

**Critical test scenarios**:
- Generated OpenAPI contains `/`, `/health`, `/ready`, and every route owned by catalog, pages, and admin modules, with the expected HTTP methods, verifying **AC-1**.
- No generated path starts with `/api/auth`, verifying **AC-1**.
- Representative request and response schemas match their canonical Zod contracts, input/output conversion is correct, and unsupported schemas fail generation rather than emit an unconstrained fallback, verifying **AC-2**.
- Protected and public operations have the correct session security and error envelope responses; Better Auth and public visitor cookie behavior are not conflated, verifying **AC-3**.
- `/docs` and `/docs-json` return the document in development/test and are not registered under production configuration, verifying **AC-4**.
- The package generator writes valid, deterministic JSON; CI uploads the resulting artifact only after required checks pass, verifying **AC-5**.
- Existing API integration tests still prove the same status codes, response envelopes, cookies, and authorization behavior after documentation metadata is added, verifying **AC-6**.

## Build plan

1. Add `@nestjs/swagger` and the OpenAPI document factory with explicit included modules and stable OpenAPI metadata. Add a route inventory test proving Letterly route inclusion and Better Auth exclusion. Satisfies **AC-1**.
2. Add `ApiZodBody`, `ApiZodQuery`, `ApiZodParams`, `ApiZodResponse`, and shared error-response decorators using Zod 4 OpenAPI JSON Schema input/output conversion. Annotate route inputs with the exact schemas already used by `ZodValidationPipe`. Satisfies **AC-2** and **AC-3**.
3. Add operation summaries, tags, success statuses, response contracts, cookie security, and applicable error statuses to health, catalog, page, and admin controllers. Add or improve feature-owned response schemas where current response types have no reusable contract. Satisfies **AC-2** and **AC-3**.
4. Mount `/docs` and `/docs-json` only outside production; add an API package `openapi:generate` script that writes deterministic ignored JSON using the same document factory. Satisfies **AC-4** and **AC-5**.
5. Update CI to generate the OpenAPI file after the existing quality gates and upload it as `letterly-api-openapi`. Add tests for generated route coverage, schema conversion, security and errors, environment gating, determinism, and unchanged HTTP behavior. Run the API unit/e2e suites, build, and root lint, formatting, type, Prisma, and build gates. Satisfies **AC-1** through **AC-6**.

## Consequences

**Positive**:
- Contributors can inspect an API contract generated from actual Nest routes and the same Zod inputs used by the server.
- Better Auth remains an SDK-owned contract rather than a duplicated auth API description.
- CI preserves a reviewable artifact for every passing build without publishing an API schema in production.
- A route inventory test makes future API route additions visible when documentation metadata is missing.

**Negative / tradeoffs**:
- Controllers require concise documentation decorators, and new routes must add contract metadata.
- Some complex response shapes may need Zod schema extraction before they can be documented clearly.
- The artifact describes route-level contracts but cannot prove provider availability, authorization behavior, or that prose accurately describes every business invariant; API tests remain authoritative for runtime behavior.
- `@nestjs/swagger` remains an application dependency because controller metadata and the nonproduction route use it, even when the production route is disabled.

## Follow-up

- Keep the document aligned with the selected cookie configuration if Better Auth changes its session cookie policy.
- If an API client generator is selected later, consume the CI artifact rather than checking in a second generated contract.
