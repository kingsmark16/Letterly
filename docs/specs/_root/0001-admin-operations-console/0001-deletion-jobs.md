# Deletion jobs

## Summary

Permanently deleting a creator or page immediately blocks access and starts tracked cleanup. Your administrator can leave the screen and return to see progress or resume a failed job. A completed job proves that applicable database records and uploaded objects have been removed.

## Requirements

Implements parent AC-4 through AC-6 and AC-9 through AC-11. Deletion has no undo or recovery window and sends no new email.

## Decision

Use durable PostgreSQL jobs and the existing media cleanup service. Extend successful cleanup acknowledgement to record job progress before removing its task row. Do not run an account cascade in an HTTP request. (basis: confirmed data model, existing MediaCleanupService and PrismaMediaCleanupRepository, Prisma transactions and explicit idempotency.)

## Feature design

### Data model

All timestamps are UTC. Required means nonnullable. Fields not explicitly nullable are required. Counts and attempts are nonnegative integers. User IDs remain strings, never coerced to UUIDs.

| Record | Fields and constraints |
| --- | --- |
| User and Page additions | Nullable `deletionRequestedAt` timestamp, default null. Presence is an irreversible access barrier until removal. |
| DeletionJob | UUID `id` primary key; `targetType` CREATOR or PAGE; `targetId` string bounded to 200; unique `(targetType,targetId)`; nullable `requestedById` User foreign key with set null; nullable `parentJobId` self foreign key; `reasonCode` existing report reason enum; nullable `note` up to 500 trimmed characters; `state`; `requestedAt`; nullable `startedAt`, `completedAt`, `nextRetryAt`, `leaseOwner`, `leaseExpiresAt`, `lastFailureCode`; `attempts` default 0; `version` default 0; page/database/media progress counts default 0; nullable `uploadsSafeAfter`. |
| DeletionJobMedia | UUID `id`; required `jobId` foreign key; nullable `cleanupTaskId` MediaCleanup foreign key with set null; nullable `completedAt`. Unique nonnull `(jobId,cleanupTaskId)`. A pending link requires a cleanup task; a completed link may have none. No object key is copied here. |
| DeletionAcceptanceReceipt | UUID `id`; required logical actorId, operation CREATOR_DELETE or PAGE_DELETE, idempotencyKey, canonicalPayloadHash, jobId foreign key, and acceptedAt. Unique `(actorId,operation,idempotencyKey)`. Retain with the job, independent of the existing 24 hour idempotency table. Do not retain the confirmation token or raw request. |
| Media processing metadata additions | On image/audio processing owners, persist nullable UUID attemptToken, processingState (IDLE, RUNNING, QUIESCED, or UNCERTAIN) default IDLE, nullable leaseExpiresAt and settledAt timestamps, and outputManifest default empty. The manifest is a distinct sorted array of at most 100 deterministic object keys, each bounded by the existing storage key validation. Keep this internal metadata until processing is quiescent and deletion has queued its keys. Existing source keys are also included. |

Jobs have many media links and zero or many child page jobs. Account children are page jobs; nesting beyond one level is rejected. Completed job retention removes its links and completed child jobs after the parent is also eligible. Never cascade away unfinished jobs. A page job already owned by another request is attached to the account job under lock rather than duplicated, preserving its original requester and reason. Audit the attachment separately. Index `(state,nextRetryAt,requestedAt,id)`, lease expiry, parentJobId, completedAt, and jobId on links.

Progress fields are `pagesTotal`, `pagesCompleted`, `databaseBatchesCompleted`, `mediaTotal`, and `mediaCompleted`. Parent page progress uses child jobs; parent media totals sum direct child and parent links without counting twice. Persist totals before removing their source records. Completion counts update in the acknowledgement transaction, not from counting remaining MediaCleanup rows. Database batch progress is informational, not a percentage of unknown total work. Schema checks prevent negative values and completed counts above known totals.

### Confirmation and endpoints

Paths are relative to `/api/v1/admin`. Every endpoint requires active administrator access and parent API protections.

| Method and path | Input | Output and status |
| --- | --- | --- |
| POST `/creators/:creatorId/deletion-preview` | expectedModerationVersion | 200 impact and signed confirmation token |
| POST `/pages/:pageId/deletion-preview` | expectedModerationVersion | 200 impact and signed confirmation token |
| POST `/creators/:creatorId/deletions` | common action body, typedTargetId, confirmationToken | 202 safe job projection |
| POST `/pages/:pageId/deletions` | same | 202 safe job projection |
| GET `/deletions` | state, targetType, exact targetId, cursor, size | 200 jobs and nextCursor |
| GET `/deletions/:jobId` | UUID | 200 safe job detail and child summary counts |
| GET `/deletions/:jobId/children` | cursor, size | 200 bounded child jobs |
| POST `/deletions/:jobId/retry` | confirm, expectedJobVersion, idempotencyKey | 202 existing job, or 409 invalid state |

Previews consume the read budget and validate origin. Impact includes page, submission, image, audio, pending upload, and related moderation record counts. It never returns their contents. The preview is a warning summary, not a promise that work cannot change. The token binds actor, target, expected version, impact digest, issuance time, and a five minute expiry using the existing signing infrastructure with a distinct purpose. Acceptance locks the same target and recomputes the impact before comparing its digest. A mismatch returns 409 `STALE_DELETION_IMPACT`; expiration requires a new preview. `typedTargetId` must exactly match the route target. Do not put signed tokens in URLs or logs.

After current actor authorization, acceptance first checks DeletionAcceptanceReceipt so a lost 202 can be replayed even after target removal or ordinary idempotency expiry. An exact actor/operation/key and canonical payload hash repeat returns 202 with the same job ID and its current safe projection; changed payload returns 409 IDEMPOTENCY_CONFLICT. The canonical hash covers route target, reason, note, expected version, typed ID, confirm, and confirmation token digest using the existing canonicalization implementation. An existing receipt is checked before preview expiry or target existence. In the acceptance transaction, authorize the current creator role, validate version and preview, set deletionRequestedAt, set moderation DISABLED, revoke creator sessions for account deletion, increment version, create/reuse the unique job, and append audit, ordinary idempotency, and acceptance receipt records. Return only after that transaction commits. Creator job acceptance blocks all its pages through the shared creator predicate. Page acceptance blocks only that page. ADMIN targets and pages owned by administrators are protected.

Receipts contain no target content, email, raw token, or request body. They remain until the associated job is eligible for retention deletion, including any delay for a retained parent. Retry commands retain the existing 24 hour replay horizon because their job remains directly readable; the extended receipt applies specifically to deletion acceptance. Once both job and receipt are purged, no replay guarantee remains and an absent target returns the ordinary safe 404. Retention must remove receipt rows transactionally with the job.

### Response allowlists and list contracts

| Response | Exact fields |
| --- | --- |
| Job summary | id, targetType, targetId, parentJobId, state, requestedAt, completedAt, version, pagesTotal, pagesCompleted, mediaTotal, mediaCompleted |
| Job detail | Summary plus requestedById, reasonCode, note, startedAt, attempts, nextRetryAt, lastFailureCode, databaseBatchesCompleted, childrenTotal, childrenCompleted, childrenNeedingAttention |
| Children response | `{items,nextCursor}`, where each item is a job summary |
| Impact preview | targetType, targetId, expectedModerationVersion, counts, confirmationToken, issuedAt, expiresAt |
| Impact counts | pages, submissions, images, audioTracks, pendingUploads, reports, moderationActions, appeals |

Fields preserve their schema nullability. Impact counts come from current target scoped database COUNT queries; pages is 1 for a page target and its owned page count for a creator. Submission count includes soft deleted submissions that will be purged. Images/audio count their records, not variants; pendingUploads counts unexpired issued grants. Detail note is the optional bounded deletion note, rendered as text. It stays out of lists, logs, analytics, and audit metadata. Preview tokens occur only in that response, never in job DTOs. LeaseOwner, leaseExpiresAt, resumeState, payload hashes, receipt keys, output manifests, storage keys, and internal processing data are never selected into these DTOs.

Job lists sort by `(requestedAt DESC,id DESC)`, default size 25, maximum 100. Children use the same order and limits under the fixed parentJobId. Normalize exact enums, trim targetId to its existing bounded contract, and require targetType whenever targetId is supplied. Signed cursors bind endpoint purpose, parent ID when applicable, all filters, size, and sort version. List envelopes are `{items,nextCursor}`. Exact target lookup returns zero or one retained job within this same envelope. Source every job field from the job row or its persisted progress; childrenNeedingAttention counts children in NEEDS_ATTENTION and childrenTotal/Completed use child job rows. Do not count vanished media tasks as success.

### Worker and concurrency

Job states are `QUEUED`, `DATABASE_CLEANUP`, `WAITING_FOR_CHILDREN`, `MEDIA_CLEANUP`, `RETRY_WAIT`, `NEEDS_ATTENTION`, and `COMPLETED`. No cancel or restore transition exists. Retry stores the prior phase and resumes it. Add `resumeState` nullable phase enum to DeletionJob for that purpose. Each claim has a random leaseOwner fencing token, a five minute lease, and a conditional state/version update. Expired leases can be reclaimed. Every acknowledgement checks current lease ownership. Use database time for lease decisions.

Run the existing Nest lifecycle scheduling pattern every 30 seconds, at most 10 claimed jobs per run with concurrency 2. Database cleanup uses at most 50 pages or 100 related rows per transaction, with at most 10 seconds per transaction. Renew or release the lease between batches. Storage calls run outside database transactions. Automatic retries allow five consecutive failed attempts with delays 1, 2, 4, and 8 minutes before NEEDS_ATTENTION. Manual retry resets the consecutive retry budget, increments version, audits the request, and resumes the same job without deleting evidence. An active lease or completed job cannot be manually retried.

Account work discovers owned pages in bounded `(id ASC)` batches and creates/adopts child jobs before processing them. Keep the disabled User row until every page child is complete, then remove sessions, accounts, verification records actually associated through the existing auth identifiers, and the User. Do not delete unrelated email verification records by a broad pattern. Actor foreign keys use existing set null behavior. Enumerate reports, moderation actions, appeals, responses/answers/messages, journey records, visits, view sessions, and media relations through schema reviewed bounded deletions before parent removal. Avoid relying on an unbounded final cascade. Preserve existing slug reservation tombstone behavior so deleted links are not silently reassigned.

After child discovery, the account job enters WAITING_FOR_CHILDREN and releases its lease. Child state changes schedule parent reconciliation in the same transaction; the ordinary scheduler also reconciles waiting parents so a lost wakeup is harmless. Any child in NEEDS_ATTENTION makes the parent NEEDS_ATTENTION with safe code CHILD_JOB_FAILED and resumeState WAITING_FOR_CHILDREN. Parent counts still distinguish completed, running, and failed descendants. When every child completes, the parent resumes its final database and media phases. A parent cannot complete merely because no currently owned Page rows remain.

Allow manual retry on an eligible failed child independently. Retrying a parent schedules reconciliation and resumes eligible failed descendants in batches of at most 50, reusing their IDs, original reasons, progress, and existing media tasks. Add nullable retryChildrenAfterId as an internal persisted cursor on the parent to continue a large retry wave across scheduler runs. Do not reset or steal active child/task leases or completed work. Reconcile the parent after child retry so it returns to WAITING_FOR_CHILDREN only when no child still needs attention. Record the parent request and each resumed child as safe audit events. A parent can remain attention required while its retry wave is still visiting other failed children.

All creator writes, draft creation, moderation restore, media authorization/finalization, visitor writes, and public reads must reject a deletion barrier. Serialize acceptance with mutations through a shared User then Page row lock order, followed by job/task rows. Include every new count changing public submission/report/upload path when enforcing the confirmation barrier. A count change before acceptance invalidates impact; a write after acceptance is refused. Job retry has its own expected version. Do not leave these predicates only in a browser guard or session cache.

Deletion also coordinates server image/audio processing already running at acceptance. Before a processor writes any source or derived object, persist its complete deterministic output manifest and claim token under the same User then Page barrier lock. A processor checks the token and deletion barrier before starting a storage write and before database finalization. After acceptance, revoke further claims and renewals, prevent a new attempt, and make the running attempt settle its outstanding storage calls without publishing results. A stale processor cannot acknowledge success. Its predeclared output keys remain part of deletion cleanup even if finalization fails.

Lease expiry alone does not prove that a storage write has stopped. Keep processing records and their output manifests until all in flight calls have settled and the attempt is marked QUIESCED. If a crashed or unresponsive processor cannot prove quiescence after its lease expires, mark it UNCERTAIN and the deletion job NEEDS_ATTENTION with PROCESSOR_QUIESCENCE_UNKNOWN. Recovery must establish that the old process is terminated and its outstanding writes have settled before resuming and performing the final object sweep. Manual Retry cannot override UNCERTAIN. Implementation must include an operations runbook for stopping the identified processing instance, establishing storage call completion, and recording the recovered attempt as QUIESCED through an audited internal recovery operation; that operation records attemptToken, operator identity, evidence reference, and database timestamp, never a blanket job success. If completion cannot be established, the job remains attention required. Never declare deletion complete while an attempt can still write. Internal processing manifests contain only bounded deterministic object keys and attempt metadata, never content, and are purged after the final acknowledged sweep. Source uploads remain subject to the separate grant cutoff below.

Before removing media records, enqueue every source and processed image/audio object through existing MediaCleanup and link tasks transactionally. Include already queued tasks for those objects. Store the latest expiry of issued upload grants in uploadsSafeAfter before deleting their records. Expiry is a lower bound for the final sweep, not proof that an earlier admitted upload has finished. The source upload settlement gate below must also pass before final deletion and acknowledgement. Existing upload expiry fields supply current grant deadlines; retain every newly issued grant through the ledger defined below so retries cannot lose an older key. Do not infer an arbitrary safe cutoff. Completed storage deletion of a missing object is success only when all writer settlement gates have passed.

Enumerate object metadata and related rows in cursor batches of at most 100. Preserve each MediaCleanup row and its object key until its linked jobs' latest uploadsSafeAfter has passed and every linked job has proven source upload settlement. The claim query defers these tasks until both conditions hold, then deletes the object and acknowledges success. A previously leased task must serialize acknowledgement with job linking and defer row removal when a new link extends the cutoff or adds an unresolved settlement gate. Lease fencing still applies.

On media success, verify task lease ownership, stamp every pending job link completedAt, update job progress, and delete the MediaCleanup task in one transaction. Never interpret a missing task as successful cleanup. An unexplained missing pending task moves the job to NEEDS_ATTENTION with `CLEANUP_RECEIPT_MISSING`. Lease loss after a storage call leaves acknowledgement to recovery. Retry reissues safe object deletion. Reuse existing media batch 50 and concurrency 4. A media task in REVIEW makes linked jobs NEEDS_ATTENTION; manual job retry releases only eligible linked REVIEW tasks, never steals active task leases or unrelated work.

Safe failure codes: `DB_TIMEOUT`, `CONSTRAINT_CONFLICT`, `STORAGE_UNAVAILABLE`, `DELETE_FAILED`, `CLEANUP_RECEIPT_MISSING`, `CHILD_JOB_FAILED`, `PROCESSOR_QUIESCENCE_UNKNOWN`, `UPLOAD_SETTLEMENT_UNKNOWN`, `UNKNOWN`. Do not store stack traces or object keys in job projections. Read progress every five seconds while its screen is visible and work is pending; pause when hidden, on completed state, or after access loss. Leaving the screen never stops server cleanup.

### Processor recovery clarification, ratified 2026-11-18

This clarification closes the missing process identity, storage settlement, and recovery authorization contract for parent AC-5, AC-6, and AC-9 through AC-11. You accepted its content after a fresh review using the same model and approval of all five corrections. The feature remains In Progress, and this design acceptance grants no authority to recover a real attempt or enable deletion.

The chosen approach is a targeted extension of the existing media records and an internal operations command. Keep the current PostgreSQL, Better Auth, Azure Container Apps, and R2 providers. No public recovery endpoint, browser override, new queue, or new identity provider is introduced. Recovery is an explicit operator attestation backed by retained evidence. The command validates the evidence structure and current database state; it cannot independently prove a provider assertion about an unobserved request.

#### Process identity and attempt ownership

Generate one UUID `processingInstanceId` with Node `randomUUID()` at API process startup. It identifies that process lifetime, is never reused after restart, and is not a lease token. Capture a bounded host identity once at startup and persist its snapshot when claiming an image or audio attempt:

| Host identity field | Source and validation |
| --- | --- |
| platform | `AZURE_CONTAINER_APPS` when Azure metadata is present; otherwise `LOCAL` only in development or test |
| appName, revisionName, replicaName | Azure supplied `CONTAINER_APP_NAME`, `CONTAINER_APP_REVISION`, and `CONTAINER_APP_REPLICA_NAME`; all required together, each 1 to 200 characters matching letters, digits, periods, underscores, and hyphens |
| hostname, processId | `os.hostname()` bounded to 253 characters and positive integer `process.pid`; local diagnostics only, not globally unique ownership |
| processStartedAt | One `SELECT clock_timestamp()` result read at process initialization and held with its boot UUID in memory, reused in its persisted claim snapshots; no separate process registry table |

For LOCAL, Azure fields are null. For Azure, hostname and processId are null, since the platform tuple and boot UUID identify the owner. For hosted production runtime, missing or partial Azure metadata prevents new media processing claims and deletion activation with a safe configuration error. A configured environment label, PID, replica name, or expired lease alone cannot substitute for the boot UUID. Do not require an operator to supply or reuse a boot UUID through environment configuration. Keep host details out of ordinary admin DTOs, logs containing user records, and metrics labels.

Add nullable `processingInstanceId` UUID, nullable `processingHostIdentity` JSON with the exact shape above, nullable `processingStartedAt`, and `storageWriteState` enum NONE, IN_FLIGHT, SETTLED, or UNCERTAIN default NONE to PageImage and PageAudio alongside the already specified attempt metadata. Use existing `processingLeaseExpiresAt` as the processing lease column rather than creating a second lease deadline. `settledAt` is the database timestamp of proven settlement. A RUNNING or UNCERTAIN attempt requires its token, instance identity, host snapshot, start timestamp, and complete output manifest. Index instance ID and processing state for bounded internal diagnostics.

An attempt token is a fresh UUID per claim, separate from the process UUID. Its manifest includes every source and possible derived key before any storage mutation. Image output comes from the existing deterministic `pages/{pageId}/images/{imageId}.webp` rule and persisted source key. Audio currently has its persisted source key and no derived output. State writes use the shared User, Page, then media row lock order and compare both token and instance ID. Do not overwrite an unresolved attempt with a new claim. A new attempt may replace settled metadata only after the prior manifest keys have been durably handed to cleanup or retained on the current media record; unresolved cleanup must never lose a key.

#### Storage settlement

Before each processor PUT or DELETE, persist IN_FLIGHT under the barrier locks, conditional on the current token and instance ID. Only after that transaction commits may the adapter send the request. The gap between recording IN_FLIGHT and dispatch is treated conservatively as a possible dispatch after a crash. After a definitive provider response, persist SETTLED before starting another mutation. NONE means this attempt has not dispatched a storage mutation. Source reads do not create objects, but the process still must pass token and barrier checks before a later write or database publication.

Use an explicit single provider request for each processor mutation. Disable both the adapter retry loop and SDK automatic retries on this tracked path. Preserve the existing retry policy for independent MediaCleanup tasks. Automatic settlement is allowed only for a definitive successful provider response, or a proven local failure before any request dispatch. Once dispatch is possible, every error, including any HTTP error, lost response, timeout, connection abort, or failure to record a terminal result, becomes UNCERTAIN. No provider rejection allowlist is implied. A locally settled promise or later successful request does not establish the outcome of an earlier unknown request. Do not issue another processor write after uncertainty. A narrower error classification would require a later documented provider guarantee and contract update.

Normal completion may mark the attempt QUIESCED only after all local calls finish and storageWriteState is NONE or SETTLED, with no earlier unresolved mutation. Acceptance of deletion prevents further claims and publication. A running process can acknowledge quiescence after it has stopped sending calls and recorded all definitive outcomes. Once an attempt is UNCERTAIN, ordinary completion, lease reclaim, and manual job Retry cannot clear it; only the recovery operation below can. Keep its media row and manifest until recovery and final cleanup finish.

Neither lease expiry, process termination, an abort signal, elapsed time, object absence from HEAD/LIST, a successful delete, nor credential revocation proves that a request already accepted by storage cannot finish later. These are useful observations, but are insufficient recovery evidence on their own. If a provider cannot establish the required outcome, the job remains NEEDS_ATTENTION with PROCESSOR_QUIESCENCE_UNKNOWN. There is no invented waiting period or automatic success fallback.

#### Internal recovery command and evidence

Canonical serialization version 1 applies only to this clarification's manifests, identity hashes, recovery evidence, and source upload settlement records. Validate the exact schema first; reject unknown fields, undefined values, duplicate JSON object keys, invalid dates, and nonfinite numbers. Normalize timestamps to `Date.toISOString()` UTC strings. Sort object keys recursively by UTF16 code unit order, serialize compact JSON with no whitespace, and hash its UTF8 bytes with SHA256 to lowercase hexadecimal. Preserve evidence text exactly, with no trimming or Unicode normalization. Sort and deduplicate manifest keys using the same code unit order. Sort evidenceRecords by lowercase UUID id and reject duplicate IDs; other arrays preserve their schema order. All UUIDs normalize to lowercase. The versioned envelope includes schemaVersion where declared. Do not reuse or change existing moderation payload hashes; the current private fixed payload helper is not a generic canonical JSON implementation.

Implement `pnpm --filter api admin:recover-media-attempt -- --job-id <uuid> --media-type <IMAGE|AUDIO> --media-id <uuid> --attempt-token <uuid> --instance-id <uuid> --evidence-file <path> --confirm`. This command runs in the selected environment through the existing controlled operations shell. It does not start HTTP listeners or schedulers. Access requires both that operations shell's database credentials and a current Better Auth session supplied through the temporary environment variable `LETTERLY_RECOVERY_SESSION_COOKIE`. Verify it through the same Better Auth provider and current active ADMIN database policy used by the API. Derive operatorId from that verified session, never from a user supplied actor ID. Do not accept a bootstrap secret as operator identity. Do not put the cookie in arguments, output, evidence, or retained state; clear it when the command exits and document clearing it from the invoking shell.

The same command supports a mutually exclusive `--inspect --job-id <uuid> --media-type <IMAGE|AUDIO> --media-id <uuid>` mode, with the same authorization. It performs no recovery write and returns only jobId, mediaType, mediaId, attemptToken, processingInstanceId, processingHostIdentity, processingStartedAt, processingLeaseExpiresAt, processingState, storageWriteState, and manifestSha256 from the current rows. This is the runbook's source for identifying the exact process and preparing evidence. It never prints a manifest, key, session, content, or provider credential. Missing or mismatched job/media relationships return a safe unavailable result.

The evidence file is a strict JSON object no larger than 16 KiB. Unknown fields are rejected. Its exact fields are schemaVersion (literal 1), jobId, mediaType, mediaId, attemptToken, processingInstanceId, manifestSha256, termination, storageSettlement, and evidenceRecords. Identifiers must match the command and locked rows. manifestSha256 is the lowercase SHA256 of the stored distinct sorted manifest serialized as JSON. File paths and object keys are not evidence identifiers and must not occur in the retained JSON.

`termination` contains platform (the stored host platform), hostIdentitySha256 (SHA256 of the stored host JSON using canonical serialization version 1), observedAt (UTC timestamp), and evidenceReference (opaque `ops:<uuid>`). For Azure, the referenced record must identify the exact app, revision, replica, and boot UUID, and establish that its process or enclosing replica is terminated and cannot resume. Restarting a replica is insufficient without evidence that the old process ended. For local synthetic tests, evidence identifies the spawned process lifetime and successful process exit. A PID reused by another process must not satisfy this check.

`storageSettlement` contains basis (NO_UNRESOLVED_WRITE or PROVIDER_CONFIRMED), observedAt (UTC timestamp), and evidenceReference (opaque `ops:<uuid>`). NO_UNRESOLVED_WRITE is allowed only when locked durable state is NONE or SETTLED, with no unknown mutation. IN_FLIGHT or UNCERTAIN requires PROVIDER_CONFIRMED: the referenced provider support or operational trace record must establish terminal completion or definitive nonacceptance for every possible mutating request from this attempt, covering its manifest, instance, and processing interval. A partial request log, generic consistency statement, timeout, or missing object is insufficient. Missing provider proof leaves the attempt unresolved, even if the process has terminated. observedAt values must be no earlier than processingStartedAt and no later than current database time. References are attestations the operator must substantiate, not a claim that the CLI has verified a remote provider trace.

Retain a bounded immutable `MediaProcessingRecovery` row containing UUID id, jobId foreign key, mediaType, logical mediaId and pageId UUIDs, attemptToken UUID, processingInstanceId UUID, logical operatorId string bounded to 200, manifestSha256, evidenceSha256, evidence JSON, and recordedAt database timestamp. evidenceSha256 hashes the validated evidence using canonical serialization version 1. Unique `(mediaType,mediaId,attemptToken)` prevents two recovery attestations for one attempt. The generated recovery ID supplies its operations reference `recovery:<uuid>`. Embed supporting proof exclusively inside this row's evidence JSON. evidenceRecords is an array of exactly the distinct referenced records, each with lowercase UUID id, kind TERMINATION or STORAGE_SETTLEMENT, and nonempty plain text up to 8000 characters. Each reference must resolve to the matching kind in this same array. IDs are scoped to this recovery; there is no global evidence table or shared retention ownership. These records contain operational proof and provider request references only, never media keys, page content, credentials, cookies, or private visitor data. Keep both input bytes and complete canonical evidence within 16 KiB. The verified operator and recordedAt on the recovery row establish who submitted the complete proof and when. These are operator supplied proof records; an opaque ID alone is not proof.

Recovery first verifies the current session and active ADMIN policy. Then check the retained unique recovery record before requiring a live Page/media row, barrier, expired lease, or UNCERTAIN state. An exact match of jobId, mediaType, mediaId, attemptToken, processingInstanceId, and canonical evidence returns the original safe result even after media removal; any changed value conflicts. Any currently authorized active ADMIN with the exact request may replay it. Preserve the original operatorId and recordedAt. Recheck current session validity and actor role/status inside the replay transaction before returning. No replay guarantee remains after job and recovery retention purges the record.

For a new recovery, acquire all relevant User locks, including the acting administrator and target creator, in ascending ID code unit order, then Page, relevant job, and media rows. Revalidate the actor's current session and role/status and the target relationship within that transaction. Require an accepted deletion barrier, exact current attempt and instance, expired processing lease by database time, UNCERTAIN processingState, and a job needing attention for processor uncertainty. Recheck the unique recovery record after locking to handle concurrent commands. Confirm the stored manifest hash and evidence. Atomically mark only that media attempt QUIESCED, set storageWriteState SETTLED and settledAt from database time, persist recovery, increment job version, and append an audit event PROCESSOR_RECOVERY_RECORDED. Its metadata allowlist is jobId, mediaType, mediaId, attemptToken, processingInstanceId, and recoveryId. The audit actor is the verified operator. Return only jobId, mediaType, mediaId, attemptToken, recoveryId, and recordedAt. Do not mark the job complete, release an active worker lease, erase the manifest, or mark media links successful. The existing confirmed job Retry resumes the final sweep after this operation. Recovery diagnostics and errors contain safe IDs/codes only.

Retain recovery and its referenced evidence with the job for the existing 730 day completed job period, including any parent delay. The operations runbook must distinguish application validated fields from the human duty to verify the supporting records.

#### Source upload settlement gate

The direct R2 upload contract remains in place. A signed grant may authorize multiple requests before expiry. Completion of one upload, a ready media row, the creator's completion callback, or grant expiry does not prove that another admitted request has stopped. No provider completion fence is currently named by this application. Consequently every issued direct upload grant requires substantiated settlement evidence before a deletion job can complete. This includes expired and previously completed grants, not just grants whose media state is UPLOADING. If that evidence is unavailable, the honest result is NEEDS_ATTENTION with UPLOAD_SETTLEMENT_UNKNOWN, never an automatic completion after a delay. This deliberately costs operator work for pages with uploaded media; changing the upload transport to remove that cost is a separate design decision.

Add an internal `PageUploadGrant` ledger with required UUID id, logical pageId UUID, mediaType IMAGE or AUDIO, logical mediaId UUID, objectKey validated by the existing storage key contract, issuedAt and expiresAt UTC timestamps from the signing adapter, and createdAt database timestamp. Page/media IDs are logical references without cascading or restrictive foreign keys, so existing owner deletion is not rejected and cannot erase this cleanup evidence. No signed URL or credential is stored. Create a distinct row for each authorization and retry before exposing its URL, under the shared User then Page barrier locks. Persist a conservative expiresAt no earlier than the actual signed URL deadline, supplied by the signing adapter, not a guessed local clock deadline. Signing may occur outside the transaction, but recheck barriers and commit the ledger before returning the URL. Failure to commit means no URL may be exposed. Include keys for grants whose URL exposure is uncertain. Index pageId/id and mediaType/mediaId; ledger writes and reads are bounded by existing upload limits and cursor batches of 100. Retain ledger rows through media replacement, expiry, and owner media/page removal so an older source key is not lost. Ordinary cleanup may delete an object, but cannot delete its grant ledger entry. This milestone promises verified completion for admin jobs only; an owner removal or a missing Page row is not proof that retained grants are settled, and unresolved evidence is not age purged.

At page deletion acceptance, the barrier freezes new grants. Add internal DeletionJob fields uploadGrantsTotal (nonnegative, default 0), uploadManifestSha256 (nullable lowercase SHA256), and uploadsSettledAt (nullable UTC timestamp). A null hash means the ledger snapshot is not prepared and blocks cleanup, even when the default count is zero. After acceptance, the worker enumerates the immutable ledger in batches of at most 100 by ascending UUID. Stream the canonical version 1 array hash, each item containing id, mediaType, mediaId, objectKey, issuedAt, and expiresAt, without loading an unbounded array into memory. Persist the final count, hash, and maximum expiresAt on the job before removing any ledger source; a crashed snapshot restarts enumeration without changing source rows. Keep rows until final settlement and acknowledged object sweep. Enqueue every distinct ledger key alongside current media and processor manifest keys. These fields and keys stay out of ordinary admin DTOs. When the prepared ledger is empty, its hash and the barrier prove no source upload is possible: store database uploadsSettledAt without operator recovery. Parent creator jobs use their page children's settlement, never a guessed aggregate cutoff.

## Consequences

Permanent deletion cannot be rolled back. Storage outages can leave a blocked target awaiting cleanup. Bounded cleanup and retained receipts add records but make completion and recovery explainable.

## Rationale

The current cleanup service already leases and retries object deletion. Linking its acknowledged success to durable jobs preserves those protections and avoids treating absence of a task row as proof. Incremental account work keeps large cascades out of request latency.
