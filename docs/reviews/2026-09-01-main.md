## Summary

The change successfully replaces branch traversal with deterministic display-order traversal and implements a page-locked, complete-list reorder transaction with stale-version checks. However, it also makes pages accept responses despite an explicit disabled setting, omits the specified creator-message editing surface, leaves expensive question mutations outside the mandatory creator rate limit, and retains a visitor navigation trap after moving back to a choice question. These are production-facing behavior and acceptance gaps that should be corrected before release.

## Major

### 🟠 Disabled responses become publicly enabled when a question exists, `apps/api/src/modules/pages/infrastructure/prisma-pages.repository.ts:528`

**Problem**: Public projection and submission scope now treat `questions.length > 0` as sufficient to enable responses even when the persisted `settings.responsesEnabled` value is false. The submission repository repeats the same override at lines 293 and 335-337, while the owner UI still reports the persisted value as "Off" in `editor-settings.tsx:106-112`. Existing pages whose creators deliberately disabled responses but retained questions are therefore silently re-enabled by this deployment, and the enabled projection also permits the visitor-message capability.

**Why it matters**: A creator can be told that private responses are off while public visitors see a response form and the API accepts answers or private messages. That is a material consent and privacy expectation regression, and it contradicts spec 0015's requirement to preserve existing private-message and submission states.

**Suggested fix**: Keep `responsesEnabled` authoritative for both public projection and submission preflight/write authorization, or introduce an explicit owner action that atomically enables it when adding the first question. Ensure the owner projection displays the same effective state, and add regression coverage for a published page with questions plus `responsesEnabled: false` proving that neither the form nor submission scope is available.

### 🟠 Creator messages cannot be authored or edited, `apps/web/src/features/pages/components/question-list.tsx:253`

**Problem**: The choice editor renders only a label input. Although `question-editor.tsx:107-110` copies `creatorMessage` into hidden draft state and lines 132-138 send an existing truthy value back, there is no control that lets a creator create, inspect, clear, or change that value.

**Why it matters**: Spec 0015 AC-5 explicitly requires question edits to update creator messages. The API and persistence layer support the field, but the owner workflow cannot perform the required operation, so the tracer bullet is incomplete and existing values are effectively immutable from the product UI.

**Suggested fix**: Add a clearly labeled creator-message input for each applicable choice, bind it to `onChoiceChange`, support clearing to null, and cover create, edit, reload, and response-impact confirmation in browser and repository tests.

### 🟠 Question mutations bypass the mandatory creator rate limit, `apps/api/src/modules/pages/pages.controller.ts:844`

**Problem**: Create, reorder, update, and delete question routes call the application service directly without consuming the creator mutation limit. Reorder is especially expensive because a single request performs two serial update passes over as many as 100 questions (`prisma-page-questions.repository.ts:641-651`) while holding the page-row lock.

**Why it matters**: An authenticated or compromised account can repeatedly hold page locks and generate hundreds of writes per request, causing avoidable database contention. The project blueprint explicitly requires route-specific limits on creator mutations, and nearby page mutation routes already use `consumeCreator` with stable rate-limit errors.

**Suggested fix**: Consume the creator rate limit before every question mutation, map exceeded/unavailable outcomes through the same stable envelopes used by other page mutations, and add controller tests proving the limiter is called and the service is not reached after rejection.

### 🟠 Back navigation traps a previously selected choice, `apps/web/src/features/pages/components/visitor-response-form.tsx:270`

**Problem**: Selecting a radio answer immediately advances through `onChange`. When a visitor presses Back, the saved radio remains checked; activating that same radio again does not fire a change event, so the visitor cannot advance while retaining the original answer. They must choose a different answer merely to continue.

**Why it matters**: The sequential journey has a broken normal path and can force visitors to submit an answer they did not intend. The required Playwright proof for sequential Secret Letter traversal does not exercise Back followed by retaining a choice, so this regression is currently invisible to the suite.

**Suggested fix**: Separate selection from navigation with an explicit Continue action, or otherwise make re-activating the checked choice advance without changing the answer. Add desktop and mobile Playwright coverage for choose, advance, Back, retain the same choice, complete the remaining questions, and submit.

## Minor

### 🟡 Canonical contracts still expose ignored graph inputs and outputs, `packages/contracts/src/questions.ts:42`

**Problem**: The create schema still exports client `key`, `displayOrder`, `endsJourney`, and `nextQuestionId` fields, and the owner/public response schemas retain optional legacy branch fields. The controller forwards accepted legacy input even though persistence silently ignores it.

**Why it matters**: Spec 0015 says the new request and response contracts omit branch fields and that the owner supplies only supported question content. Keeping them in the shared public TypeScript/Zod surface invites consumers to send or depend on values that are intentionally discarded, making the API misleading and extending the migration indefinitely.

**Suggested fix**: Remove these fields from the canonical exported request and projection schemas. If deployed-client compatibility is required, isolate it in a legacy ingress adapter that strips the fields before producing the canonical DTO rather than advertising them in the current contract.

- Public mapping and submission validation sort deterministically by `displayOrder`, ignore legacy graph destinations, and snapshot answers in the same linear order.
- Focused repository, controller, and Playwright tests cover server-generated question keys, append order, invalid/foreign/duplicate/stale reorders, keyboard reorder controls, persistence after reload, and branch-control removal.

## Test coverage

The configured Jest/Supertest-style suites provide useful focused coverage of repository and controller behavior, and Playwright exercises owner create, edit, delete, reorder, stale retry, reload persistence, and accessible controls. Coverage is insufficient for the issues above: there is no Secret Letter browser journey proving the complete sequential visitor flow (including Back with an unchanged choice), no creator-message authoring/editing path, no controller rate-limit assertion for question mutations, and the disabled-response tests currently codify the contradictory behavior instead of preserving the owner setting.
